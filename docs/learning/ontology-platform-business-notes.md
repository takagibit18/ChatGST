# 育儿补贴本体智能体平台 — 功能与业务分析

---
## 一、平台定位

一个面向**政府育儿补贴政策**的智能体工作台，核心能力是：

> **把"生硬的政策文件"变成"可对话的智能体"，让老百姓用自然语言描述自己的情况，就能立刻知道是否符合补贴条件、需要补充哪些材料。**

业务流程覆盖：政策文档采集 → AI 自动建模 → 人工校对 → 智能体生成 → 规则引擎判定 → 审批发布 → 远程部署。

## 二、业务场景与用户角色

### 2.1 典型业务场景

| 场景        | 用户        | 描述                             |
| --------- | --------- | ------------------------------ |
| **政策录入**  | 政策分析师     | 将各省市育儿补贴政策文件上传到平台，触发自动化知识提取    |
| **规则建模**  | 本体工程师     | AI 自动从政策文档提取规则，人工逐条审核校对        |
| **智能体构建** | 系统开发者     | 基于模板一键生成针对特定政策（如"北京市育儿补贴"）的智能体 |
| **资格预审**  | 普通市民/政务人员 | 用自然语言描述家庭情况，智能体告知是否满足补贴条件      |
| **政策咨询**  | 普通市民      | 对话式问答：怎么申请？需要什么材料？去哪里办？        |
| **多地域对比** | 管理层       | 对比不同省市补贴标准差异，辅助决策              |
| **版本管理**  | 管理员       | 政策更新后新建版本，重新建模、审核、发布           |
| **远程部署**  | 运维/管理员    | 审核通过的智能体发布到生产环境                |

## 四、技术选型与业务匹配度分析

### 4.1 核心命题：为什么需要"本体 + LLM + 规则引擎"三层？

育儿补贴这类政府业务有三大特点：

| 业务特征                          | 纯 LLM 方案的问题                       | 本平台方案                                              |
| ----------------------------- | --------------------------------- | -------------------------------------------------- |
| **规则精确性要求高**（符合条件就领钱，不符合就不能领） | LLM 可能"幻觉"生成不存在的规则，或对同一条文给出不一致的判断 | 规则引擎（onto-platform）提供**确定性判定**，LLM 只做语义理解和对话       |
| **政策频繁变化**（各省市、各年度政策不同）       | 每次变化都需重新 fine-tune 模型，成本高         | 本体平台支持**版本化管理**，新政策 → 新建版本 → 重新建模，不影响旧版本           |
| **需要可解释性**（为什么不符合？缺什么材料？）     | LLM 推理过程黑盒                        | 规则引擎返回**missing 字段列表**（算子名 + 中文说明 + 提示），可追溯每条命中的规则 |

### 4.2 各技术组件的业务价值

| 技术组件                     | 业务角色       |  匹配度  | 说明                                                                                           |
| ------------------------ | ---------- | :---: | -------------------------------------------------------------------------------------------- |
| **pi-coding-agent**      | 对话引擎       | ★★★★★ | 开源成熟框架，自带工具系统、会话管理、Skills 机制、流式输出；bridge 通过 SDK 直接复用，无需自研对话框架                                |
| **DeepSeek V4 Flash**    | 语义理解       | ★★★★☆ | 国产模型，中文能力强；通过 pi-ai 统一 API 层接入，未来可切换其他模型                                                     |
| **本体平台 (onto-platform)** | 规则管理 + 判定  | ★★★★★ | 自研/定制系统，专门为政策规则设计的 extract/derive/merge 流水线，非通用方案                                            |
| **KELE 规则引擎**            | 规则执行       | ★★★★☆ | 编译为 .so 保护 IP；处理本体规则的形式化推理                                                                   |
| **SKILL.md 模板**          | Agent 行为定义 | ★★★★★ | 用 Markdown frontmatter + 自然语言定义 Agent 行为，非技术人员也能理解和修改；模板化复制机制（agent-template.ts）降低多政策场景的构建成本 |
| **jiti 动态编译**            | 工具热加载      | ★★★★☆ | Agent 工具用 TypeScript 编写，运行时动态编译，无需重启服务即改即生效                                                  |
| **SQLite (sql.js)**      | 轻量持久化      | ★★★★☆ | 零配置、无服务端依赖，适合单机/内网部署；3秒批量落盘设计平衡性能与可靠性                                                        |
| **Vite + React/Vue**     | 前端         | ★★★★☆ | 现代化 dev server，热更新；frontend/dist 可产出静态文件                                                     |
| **MinIO**                | 文件存储       | ★★★☆☆ | S3 兼容对象存储，适合存储政策文档附件；当前使用有限                                                                  |
| **PM2**                  | 进程管理       | ★★★★☆ | 守护 Node 进程，自动重启，日志管理                                                                         |

### 4.3 架构亮点

| 亮点               | 说明                                                                             |
| ---------------- | ------------------------------------------------------------------------------ |
| **Skill 自包含设计**  | 每个 Skill 目录下有独立的 SKILL.md + tools/ + config.json，Agent 可独立打包分发，不依赖 bridge 全局配置 |
| **断点续跑**         | Step2 建模每一步成功即标记 done，支持失败后从断点恢复，避免重复调用 LLM 浪费 tokens                          |
| **两阶段合并**        | merge-all 的 dry_run → 冲突决策 → commit 三步骤，确保大规模多地域规则合并的安全性                       |
| **判定历史追溯**       | 每次规则引擎调用后，从本体平台拉取规则全集，反推命中了哪些规则，写入判定历史                                         |
| **模板化 Agent 生成** | 从 policy-template 复制 SKILL.md，替换名称/描述/凭证，一键生成新政策场景的智能体                         |
| **代码保护**         | 核心 Python 逻辑 + KELE 引擎编译为 .so 机器码，保护算法 IP                                      |
| **多版本并存**        | 支持同一项目的多个版本并行开发，审批流控管发布节奏                                                      |

### 4.4 可改进方向

| 问题 | 影响 | 建议 |
|------|------|------|
| step2-finalize 中 extract/derive/merge 耗时均写死为 0 | 无法追踪各阶段真实性能 | 补全计时逻辑 |
| Docker 权限未授予 bridge 用户 | 无法管理容器化服务 | 添加 docker 组权限或使用 sudo |
| Bridge 无 HTTPS | 公网传输明文，JWT token 可能被窃取 | 配置 Nginx 反代 + Let's Encrypt |
| config.json 含明文密码 | 配置文件泄露风险 | 全部改用 crypto.ts 的 RSA 加密存储 |
| 前端 Vite dev server 直接对外 | 非生产模式，性能差 | 构建 dist 后用 Nginx 托管 |
| 部分模块无测试覆盖 | 重构风险 | 补充 vitest 单元测试（pi 框架已支持） |

## 五、端到端业务流程

```
┌────────────────────────────────────────────────────────────┐
│  1. 数据准备                                               │
│  政策分析师上传各省市育儿补贴政策文件(.md/PDF)              │
│    ↓                                                       │
│  2. 自动建模 (Step 2)                                      │
│  AI 提取问答项 → 推导规则 → 自动合并 → 消除冲突           │
│    ↓                                                       │
│  3. 人工审核 (Step 2-B)                                    │
│  本体工程师逐条校对规则，标记 Golden 用例，运行黄金集测试    │
│    ↓                                                       │
│  4. 智能体构建 (Step 3)                                    │
│  选择模板 → 关联 policyId → 生成 Agent Skill + 工具        │
│    ↓                                                       │
│  5. 测试验证                                               │
│  在对话界面模拟市民提问，验证规则引擎判定结果               │
│    ↓                                                       │
│  6. 审批发布 (Step 4)                                      │
│  提交审核 → ≥2 名审核员批准 → 发布到生产环境                │
│    ↓                                                       │
│  7. 运行服务                                               │
│  市民通过政务 App/小程序 → Agent 对话 → 规则引擎判定       │
│  → 返回资格结果 + 材料清单 + 办理指引                       │
└────────────────────────────────────────────────────────────┘
```

## 六、与业务的整体匹配度评估

| 维度 | 评分 | 评语 |
|------|:---:|------|
| **政策覆盖度** | ★★★★☆ | 15 个策略本体，覆盖多个省市，骨架模板可快速扩展新地域 |
| **准确性** | ★★★★★ | 规则引擎确定性判定 + 人工审核双重保障 |
| **可解释性** | ★★★★★ | 每条规则可追溯到原始政策条款，missing 字段提示具体缺失项 |
| **扩展性** | ★★★★☆ | 模板化 Agent 生成，新政策场景只需配置即可，但依赖本体平台 API 可用性 |
| **易用性** | ★★★★☆ | 前端 Web 界面操作，自然语言对话交互；但建模流程对非技术人员仍有门槛 |
| **安全性** | ★★★☆☆ | JWT + RSA + bcrypt 基础到位，但 HTTPS 缺失、明文配置是短板 |
| **运维友好度** | ★★★★☆ | PM2 进程守护 + systemd + Nginx 方案成熟，但部分端口裸奔 |
| **国产化适配** | ★★★★★ | 国产 Linux + 国产 LLM，全链路国产化 |

**总结**：这是一个**技术与业务高度匹配**的垂直行业智能体平台。核心创新在于将"本体建模流水线"与"LLM Agent 对话"紧密结合，让规则引擎保证判定精确性，让 LLM 处理自然语言交互，各司其职。适用于任何需要将政策法规转化为智能问答系统的政务场景（社保、医保、公积金、人才引进等）。
