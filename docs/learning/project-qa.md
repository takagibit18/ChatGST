# 项目设计决策与技术价值


---

## 一、架构设计

**Q: 为什么采用"LLM + 本体知识图谱 + 规则引擎"三层架构，而不是纯 LLM 方案？**

政务政策判定要求结果 100% 精确——"符合就领钱、不符合就不能领"，LLM 的幻觉在此场景不可接受。三层架构中各司其职：LLM 负责自然语言理解和对话交互，本体知识图谱负责将政策文档结构化为可计算的规则，规则引擎负责确定性判定。LLM 即使"理解错了"，规则引擎也会基于形式化算子给出唯一结论，不会凭空编造一条不存在的补贴标准。

**Q: 本体在系统里到底起什么作用？不是 RAG 就能搞定吗？**

RAG 解决的是"找到相关文档段落"，但政策判定不是检索问题——用户问"我能领多少钱"，RAG 能返回补贴标准那一段文字，但无法根据用户的具体条件（户籍、年龄、收入）计算出金额。本体把政策条款拆成了可计算的算子（23 个概念 × 202 个判定维度），每个算子有明确的输入条件、输出结论和提示模板，规则引擎基于这些算子做的是推理而非检索。

**Q: 规则引擎判定为什么比 LLM 直接判断好？**

三个原因：可追溯——每条判定结果关联到具体算子 ID → 原始政策条款，审计时能说清"为什么不符合"；可版本化——政策变了更新本体即可，新旧版本并存，不会出现 LLM 记住了旧政策却不知道新政策的情况；缺失提示精确——引擎返回的 missing 字段来自预设的算子定义（如"婴幼儿年龄(月)：说X岁填 X*12"），不是模型临时生成的泛泛之谈。

## 二、Agent 设计

**Q: 为什么选 pi-coding-agent 而不是 LangChain 或自研？**

pi 是一个定位明确的编码 Agent 框架，自带成熟的工具系统（read/bash/edit/write）、会话管理、Skills 机制和流式对话，且用 TypeScript 编写，与 bridge 的 Node.js 技术栈一致。LangChain 生态更重、抽象层更多，不适合需要精细控制工具调用和行为约束的场景。pi 的 Skill 机制（SKILL.md + tools/*.ts + config.json 自包含）天然适合政务多政策场景——每个政策可以打包为一个 Skill，独立分发、独立版本管理。

**Q: Skill 为什么设计成自包含的（SKILL.md + tools/ + config.json），而不是全局配置？**

政务场景的特点是"政策多、变化快、各地不同"。北京市育儿补贴和攀枝花市育儿补贴的政策逻辑不同，如果放在全局配置里，会互相干扰、测试困难。自包含设计让每个 Skill 成为独立单元：复制目录即可生成新政策的 Agent，修改 SKILL.md 不影响其他政策，tools/ 里的规则引擎工具通过 config.json 指向不同的 policy_id，实现"一套代码、多政策复用"。

## 三、建模流水线

**Q: Extract → Derive → Merge 三阶段流水线为什么不一步到位？**

一步到位意味着 LLM 直接从原始政策文档生成最终规则库，这在面对 100+ 页政策文件时 token 开销巨大且无法校验中间结果。三阶段拆解后：Extract 阶段从自然语言提取结构化 QA 对，Derive 阶段从 QA 对推导规则，Merge 阶段合并多地域规则并自动解决冲突——每阶段产出可审计、可中断、可单独重跑，出了问题不需要从头再来。

**Q: Merge 阶段的冲突检测为什么用硬规则而不是 LLM？**

冲突检测是在已经结构化的规则字段（算子名称、条件、结论）上做键值比对，不需要语义理解，硬规则比 LLM 更快、更确定、零 token 消耗。LLM 的作用在更上游——把自然语言政策文本变成结构化规则这一步。

## 四、工程实践

**Q: SQLite 选型（sql.js）是什么考虑？**

政务内网环境通常不允许安装数据库服务，sql.js 是纯 JavaScript 的 SQLite 实现，零依赖、零配置、单文件存储，npm install 完就能跑。3 秒批量落盘的设计在写入性能和断电安全之间取了平衡——政务场景写入频率低（建模结果、用户操作日志），不需要实时逐条 fsync。

**Q: jiti 运行时编译 Agent 工具有什么好处？**

Agent 的工具文件（tools/*.ts）在收到对话请求时才由 jiti 动态编译加载，不需要重启服务就能修改或新增工具。对于政策快速迭代的场景——比如上线后发现有新的判定条件需要加工具——直接编辑 .ts 文件即可生效，无需重新构建部署。
